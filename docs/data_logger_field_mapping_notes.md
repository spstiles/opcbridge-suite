# Data Logger Field Mapping Notes

## Goal

Implemented for MySQL logger jobs: allow each logger job to map tag values and
metadata into custom database fields.

By default the logger writes a fixed schema such as connection, tag name,
description, timestamp, datatype, quality, and value. That is useful for a
generic tag log, but some databases or reports need specific column names and
field layouts.

## Use Cases

- Store a tag value into a customer-specific column name.
- Include or omit standard metadata fields per logger.
- Rename standard fields such as `tag_name`, `tag_description`, or `value_text`.
- Store static fields with each row, such as site, area, report name, or unit.
- Map one tag's description into a separate database column.
- Support existing external database/report tables without requiring them to use
  opcbridge's default schema.

## Configuration

Use an optional `field_map` section on a logger job. SCADA exposes this as
**Column mapping** in the Log Job editor. Turning customization off restores the default
schema; a mapping selects only the listed source fields. Each live tag or
historian summary field still produces one row.

Example:

```json
{
  "id": "hourly_flow_log",
  "database_id": "histdata",
  "table": "flow_history",
  "tags": [
    {
      "connection_id": "plant",
      "name": "Flow.Total",
      "description": "Plant total flow"
    }
  ],
  "field_map": {
    "timestamp_ms": "sample_time_ms",
    "connection_id": "source_connection",
    "tag_name": "source_tag",
    "tag_description": "description",
    "value_numeric": "flow_value",
    "quality": "quality_code"
  },
  "static_fields": {
    "site": "Racine",
    "system": "Wastewater"
  }
}
```

## Behavior and validation

Known source fields are `job_name`, `timestamp_ms`, `timestamp_dt`,
`connection_id`, `tag_name`, `tag_description`, `datatype`, `value_numeric`,
`value_string`, `quality`, and `created_at`. Existing output-name and description
settings apply before mapping. Numeric values and booleans use `value_numeric`;
text values use `value_string`, matching the default logger behavior.

`static_fields` accepts strings, numbers, booleans, and null. It can also extend
the default schema without a `field_map`. Destination names must be unique
(case insensitive), contain only letters, digits, and underscores, begin with a
letter or underscore, and be at most 64 characters. Table names follow the same
rule. Unknown source fields and malformed configurations fail saving/reloading.

Custom mappings require an existing table. The logger checks destination columns
before writing, fails clearly if any are missing, and does not create or alter
custom tables. Unmapped columns must accept defaults/null or be generated by the
database. Database types and constraints still apply. Default jobs retain their
automatic table creation and description-column migration. Static fields require
existing destination columns in either mode.

Turning off **Customize destination columns** removes `field_map`. The save API accepts `field_map: null`
as a removal marker and omits it from persisted configuration. Direct logger
configuration should omit the key to restore defaults. An empty mapping is only
valid when at least one static field exists.

Tag CSV upload/download remains focused on tag selection. This feature does not
change historian storage or add computed fields or multiple-tag wide rows.
